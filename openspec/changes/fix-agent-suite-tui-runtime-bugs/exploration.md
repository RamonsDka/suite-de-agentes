## User-reported bug report (verbatim, translated)

1. Opening with `Alt+S` renders the new, bigger, differently-designed window, but it opens **cut off on one side of the screen**, with **a "shadow" of another, larger window visible behind it**.
2. Keyboard shortcuts in general don't work.
3. Clicking a button with the mouse does not work.
4. Arrow-key navigation works, but pressing **Enter does nothing**.
5. There is **no way to exit/quit** the window from inside it — the user has to close the entire terminal.
6. Overall it looks "a bit rough / unpolished".

## Current State

`opencode-agent-suite` v0.1.0 registers a TUI plugin via `@opencode-ai/plugin` `TuiPlugin` (`src/tui/index.tsx:662`, exported as `tui`). `Alt+S` is bound through `api.keymap.registerLayer` (`registerSuiteKeymap`, `src/tui/index.tsx:578`) to open `openSuiteSafely` (`src/tui/index.tsx:632`), which mounts a **custom OpenTUI/Solid component tree** (`Landing`, `Catalog`, `Detail`, `Modify`, `Create` — `src/tui/screens/*.tsx`) as `children` of the host's `api.ui.Dialog({ size: "large", ... })` (`src/tui/index.tsx:635-652`), wrapped in `safeScreenMount` (`src/tui/screens/nav.ts:3`) which silently falls back to the legacy `DialogSelect`-based flow only if mounting throws `"No renderer found"`.

Since the user confirms the **new** graphical design renders (not the legacy fallback), `safeScreenMount` is succeeding — the custom OpenTUI renderer context is available in production. This matches `@opencode-ai/plugin`'s `dist/tui.d.ts:459-494`: `TuiPluginApi` exposes a single top-level `renderer: CliRenderer` (from `@opentui/core`) shared by the **whole host TUI window** — i.e. there is exactly one real terminal renderer, and the plugin's OpenTUI/Solid tree is mounted inside it via the host's `Dialog` component, not a second independent renderer process.

`TuiDialogProps.size` (`dist/tui.d.ts:74-75`) only accepts `"medium" | "large" | "xlarge"` — a *relative* box size inside the host's dialog stack, not "the whole terminal". The plugin only ever requests `"large"` (never `"xlarge"`), so the Dialog's real on-screen box is some sub-region of the terminal, not the full terminal.

## Judgment Day Round 1 corrections (applied after dual blind-judge review)

Two independent judges (Judge A, Judge B) reviewed this audit against the real source. Zero CRITICALs found; no contradictions between judges. Their corrections are folded into the sections below (marked inline) plus these standalone additions:

- **Confidence correction**: Symptom 1 is downgraded from HIGH to MEDIUM — the causal link from `useTerminalDimensions()` reading full-terminal size to the specific "cut off + shadow" visual depends on an unverified assumption (whether `size:"large"` actually allocates less than the full terminal), which the original Open Questions already flagged as unresolved. The code fact itself (verified against `node_modules/@opentui/solid`) remains solid.
- **New alternative hypothesis for Symptom 1 (missed in Round 1)**: `close(api)` (`index.tsx:91-93`) calls `api.ui.dialog.clear()` and separately re-mounts via `api.ui.dialog.replace(...)`; `openSuiteSafely` (bound to Alt+S) has no re-entrancy guard against being invoked while a Suite dialog is already open. A `clear()`/`replace()` ordering issue or a re-entrant Alt+S press could independently produce a stale previous frame — a more literal "ghost window" explanation not previously considered.
- **New alternative hypothesis for Symptom 1 — vertical overflow, not just horizontal**: `Catalog`'s page-size calculation also derives from the full-terminal `dimensions().height` (`src/tui/screens/catalog.tsx:37-39` via `layout.ts`), not just `catalogColumns(width)`. Vertical row overflow past the Dialog's real bottom border is at least as likely a contributor as horizontal column overflow — both share the same root cause but the original writeup only discussed width.
- **New candidate root cause for Symptoms 4/5 (higher-value than the host-interception theory alone)**: Every selection path (`Catalog.selectFocused`, `Detail`/`Modify` `onSave`, `Create.submitField`, `Landing.select()`) synchronously calls `close(api)` → `api.ui.dialog.clear()` then `api.ui.dialog.replace(...)` **from inside the active screen's own `useKeyboard` keypress callback** — which is registered on the very `renderer.keyInput` emitter being mutated mid-dispatch (`index.tsx:620-625` inside `Catalog`'s Enter handler, mirrored in every other screen). This is a plugin-side re-entrancy hazard that could break the keypress listener or leave the dialog stack inconsistent — a concrete, fixable, plugin-side candidate that should be investigated *before* assuming the host is intercepting Enter/Escape.
- **Correction — "identical pattern across all 5 screens" claim was wrong**: `Landing.tsx`'s `useKeyboard` handler (`landing.tsx:23-32`) calls `key.preventDefault()` **only** in the `escape` branch; the arrow and Enter branches never call it. Every other screen (`Catalog`/`Detail`/`Modify`/`Create`) calls `preventDefault()` on every handled branch. Landing is the *first* screen shown after Alt+S, so this inconsistency is hit immediately by every user. This does not by itself prove Landing's Enter is broken differently from the other screens (the selection logic still runs regardless of `preventDefault`), but it means the five screens are **not** uniformly implemented, weakening the "single shared host-level cause, unrelated to plugin code" framing.
- **Correction — `safeScreenMount` description was imprecise**: the catch block in `src/tui/screens/nav.ts:3-12` falls back to the legacy flow on **any** thrown error, not only `"No renderer found"`; the substring check only gates whether `console.error` logs, not whether the fallback happens. Arbitrary component bugs are therefore also silently downgraded to the legacy dialog UI, not just genuine host-renderer absence. Additionally, every call site in `index.tsx` passes a 3rd argument (a fallback-close callback) to `safeScreenMount`, but its signature only accepts 2 parameters — that fallback callback is silently dropped everywhere, so failed-mount cleanup never runs.
- **New Open Question (missing in Round 1)**: is `api.ui.dialog.replace(...)` / `api.ui.dialog.clear()` symmetric for a custom-renderer-mounted child, or could a mismatch there independently explain a stale/ghost frame (Symptom 1) and/or an exit that doesn't fully tear down the embedded renderer (Symptom 5)? Not answerable from this repo (same host-runtime limitation as the other host-side open questions).
- **Additional real code findings out of scope for the 5 reported symptoms but worth fixing alongside them**: `Catalog`'s pagination is forward-only (`index.tsx:624` `onPage={() => undefined}` is a dead no-op; only `pagedown` is handled, no way back to earlier pages without closing and reopening); `host-compat.ts`'s `rendererMissingReported` variable is write-only dead state; `"No renderer found"` failures are never logged anywhere (zero diagnostic signal if the custom renderer silently becomes unavailable); `create.tsx` may double-fire `submitField` on Enter (both the `<input onSubmit>` and the component-level `useKeyboard` handler call it for text-input steps).

## Root Cause Hypotheses (ranked by evidence strength)

### Symptom 1 — window cut off / "shadow of a bigger window" (MEDIUM confidence — downgraded from HIGH after Judgment Day review, code-grounded but the full causal chain needs host-side confirmation)

- `Landing.tsx:17` and `Catalog.tsx:116` both call `useTerminalDimensions()` from `@opentui/solid`. Its implementation (`node_modules/@opentui/solid/index.js.map`, `useTerminalDimensions`) returns `{ width: renderer.width, height: renderer.height }` — i.e. **the full host terminal's dimensions**, sourced from the single shared `CliRenderer`, not the actual allocated box size of the `"large"` Dialog the component is mounted inside.
- `Landing.tsx:34` uses that global height to decide `compact()` (`dimensions().height < 20`) and then lays out two 24-column-wide panels **in a row** (`Landing.tsx:45,65`) when not compact.
- `Catalog.tsx:119` passes the same global `dimensions().width, dimensions().height` straight into `buildCatalogPage(...)` to compute `catalogColumns(width)` (`src/tui/layout.ts:1-5`) and page size.
- **Conclusion**: every screen makes its column-count / compact-vs-row / page-size layout decisions against the *entire terminal window*, not against the actual pixels the host gave the Dialog (`"large"`, which is smaller than the full terminal by design — dialogs are meant to look like an overlay, not fill the screen). On a real terminal that is tall/wide enough overall, the components will choose a *wider/multi-column, row-oriented* layout than the `"large"` box can actually display, so content overflows past the Dialog's real border. The host's own Dialog chrome (border box sized to `"large"`) stays underneath/behind the overflowing content — this is very plausibly what the user is describing as "opens cut off on one side" with "a shadow of another, bigger window" behind it: two differently-sized boxes (the real `"large"` dialog frame vs. the content laid out for the full terminal) are simultaneously visible.
- This is a genuine implementation bug: `size: "large"` is being used as the mount point while every screen's responsive logic assumes it owns the full renderer surface. Either the screens need a way to read the *actual allocated Dialog box size* (if the host API exposes it — not found in `tui.d.ts` today) or the Dialog should be requested at `"xlarge"`/full-bleed and screens should stop trusting `useTerminalDimensions()` for anything other than a genuinely fullscreen surface, or the components need to measure their own root box (e.g. an OpenTUI resize/layout callback on the root element) instead of the renderer's raw terminal size.

### Symptom 4 — arrows work, Enter does nothing (MEDIUM confidence)

- Every screen's `useKeyboard` callback (`Landing.tsx:23`, `Catalog.tsx:132`, `Detail.tsx:86`, `Modify.tsx:51`, `Create.tsx:111`) checks `key.name === "return" || key.name === "linefeed"` for Enter and `key.name === "escape"` for exit — these key names **do** match `@opentui/core`'s own internal keybinding vocabulary (confirmed via `node_modules/@opentui/core/index.node.js:6392-6698`, which defines `{ name: "return", ... }` / `{ name: "linefeed", ... }` bindings), so this is not a naming typo in the plugin code itself.
- `useKeyboard` (`@opentui/solid`) subscribes to a **single shared** `renderer.keyInput` event emitter (`keyHandler.on("keypress", callback)`) — the same renderer instance exposed to the whole host TUI. Arrow keys are simple, universally-forwarded ANSI escape sequences; **Enter and Escape are exactly the two keys a host terminal-dialog framework is most likely to intercept globally** for its own default "confirm/cancel this dialog" semantics before forwarding raw input down to an embedded child's `keyInput` emitter. That would explain arrows reaching the plugin's handler while Enter/Escape do not, with a single shared code path (no separate bug per screen — all five screens use the identical pattern and would all be affected identically, matching the report of a single, general problem).
- This cannot be fully confirmed from this repository alone — the exact host-side raw-input dispatch logic (which keys the host's own dialog stack consumes vs. forwards to a mounted custom-renderer child) lives inside the OpenCode host runtime itself, not in this plugin's `node_modules` or source. Recommended next step before implementing a fix: reproduce with `console.error`/log-based instrumentation of `renderer.keyInput` inside a debug build, or ask the OpenCode host team/docs whether `Dialog`-mounted custom children reliably receive `return`/`escape` keypress events.

### Symptom 5 — cannot exit except by closing the terminal (MEDIUM confidence, likely same root cause as #4)

- Every screen wires `escape` → `props.onClose()`/`props.onBack()`/`props.onCancel()`, which routes back to `close(api)` → `api.ui.dialog.clear()` (`src/tui/index.tsx:91-93`). The wiring is present and correct on the plugin side.
- If Escape (like Enter) never reaches the embedded renderer's `keyInput` emitter (see Symptom 4), `close(api)` is simply never called, which fully explains "no way to exit — must close the terminal": there is no code-level *fallback* exit path (no `Ctrl+C`/`q` handler, no host-level dialog-stack default Escape binding wired independently of the custom screens).
- **Actionable, low-risk mitigation** regardless of the exact host root cause: add a host-level `keymap` binding for the dialog-closed case (e.g. a chorded/`Ctrl+` fallback registered through `api.keymap.registerLayer` rather than only through the embedded OpenTUI `useKeyboard`) so users always retain a host-guaranteed way out even if the embedded renderer's raw keypress forwarding is unreliable for a given key.

### Symptom 3 — mouse clicks don't work (MEDIUM confidence)

- `onMouseDown={props.onSelect}` **is** wired on the actual interactive boxes (`catalog.tsx:107`, `detail.tsx:61`, `modify.tsx:28`, `create.tsx:78`) — the click handlers exist in source and are not missing/stubbed.
- Given Symptom 1's finding that these boxes are laid out using the *wrong* (global-terminal-sized) coordinate space relative to where the Dialog is actually painted, the **on-screen visual position** of a button and its **actual hit-test bounding box** inside the renderer's layout tree can diverge whenever the Dialog's real box origin/size differs from the full terminal — i.e., what the user sees as "the button" and what OpenTUI thinks occupies that screen region are not the same rectangle. Clicking where the button visually appears would then miss its real hit-test area. This is the same coordinate/sizing root cause as Symptom 1, not a separate missing-handler bug.
- Alternative/independent explanation not ruled out: mouse-tracking terminal modes (SGR mouse reporting) may not be enabled at all for an embedded custom-renderer child mounted inside a host Dialog (as opposed to a genuinely standalone OpenTUI app, which typically enables its own mouse mode on startup) — this, too, would need host-side confirmation.

### Symptom 2 — "shortcuts in general don't work" (LOW confidence, likely a restatement of #4/#5)

- No separate evidence found; most likely this is the user's general impression driven by Enter/click/exit not working (Symptoms 3-5), rather than a distinct bug. `Alt+S` itself demonstrably *does* work (the window opens), so the plugin-level `keymap.registerLayer` binding path is functional at least for that one binding.

## Test Coverage Gaps (why 75/75 passing tests + an approved review did not catch any of this)

- `test/screens.test.tsx` imports `Detail`, `Modify`, `Create` and only asserts `expect(Detail).toBeTypeOf("function")` / `expect(Modify).toBeTypeOf("function")` / `expect(Create).toBeTypeOf("function")` (lines 60, 76, 108) — **the components are never mounted through the real (or even a fake) OpenTUI renderer**, never receive a simulated `key.name` event, and never receive a simulated mouse event. Every other assertion in that file targets *pure helper functions* (`buildDetailView`, `confirmDeleteAction`, `buildModifyEffortOptions`, `createDraftAtStep`, `updateCreateDraft`, `validateCreateDraft`, etc.) — real, valuable coverage of business logic, but zero coverage of rendering, sizing, keyboard dispatch, or mouse dispatch.
- `test/tui-registration.test.ts`'s `dialogHost()` mock (per the prior `redesign-agent-suite-tui/exploration.md`) fakes `api.ui` Dialog components at the level of the **legacy** `DialogSelect`/`DialogAlert` API, not the OpenTUI/Solid custom-renderer path exercised by `Landing`/`Catalog`/etc.
- No test in the repo simulates `useTerminalDimensions()` returning a value different from a component's actual allocated box size, and no test simulates raw terminal `keypress`/mouse events through `renderer.keyInput` — so the exact class of bug reported here (host-vs-child dimension mismatch, and possible host-level Enter/Escape/mouse interception) was structurally unreachable by the existing suite. This matches and confirms the prior finding recorded in Engram (`sdd/redesign-agent-suite-tui/verify-blocker`, id 5834): "OpenTUI native FFI is unavailable in the current Node runtime, so deterministic component contracts and host-double integration tests provide runtime evidence" — the test environment could not exercise the real renderer at all, so "review approved" and "75/75 passing" never meant "verified to work in a real terminal."

## Open Questions (need host-side confirmation, not answerable from this repo)

1. Does `@opencode-ai/plugin`'s host runtime expose (or could it expose) the **actual allocated Dialog box width/height** to a mounted child, instead of only the full-terminal `renderer.width`/`renderer.height`? If yes, that's the correct fix input for Symptom 1/3. If no, is `"xlarge"` effectively full-terminal (making the mismatch moot at that size)?
2. Does the host's own dialog-stack keyboard handling consume `return`/`escape` before forwarding to a mounted custom-renderer child's `keyInput` emitter, or should those always pass through? (Determines whether Symptoms 4/5 are a plugin-side wiring bug or a host-integration limitation needing a documented workaround.)
3. Is SGR/mouse-tracking terminal mode enabled by the host for the shared `CliRenderer` by default, or does a plugin need to opt in explicitly for its mounted children to receive mouse events?

## Recommended Fix Direction (high level — not a full design)

1. Stop trusting `useTerminalDimensions()` as "my available box size" in `Landing`/`Catalog` (and any future screen). Either request `size: "xlarge"` and treat that as full-bleed, or measure the actual mounted root box (if OpenTUI/the host exposes a resize/layout callback on the root element) and drive `compact()`/`catalogColumns()`/pagination (both width AND height) off that instead of the raw terminal size.
2. Investigate and fix the synchronous dialog-stack mutation from inside the active `useKeyboard` keypress callback (`close(api)` + `dialog.replace(...)` called directly from `onSelect`/`onSave`/`submitField` handlers) — defer navigation with a microtask/scheduler tick instead of mutating the dialog synchronously inside the keypress callback that owns the listener being mutated. Do this *before* assuming Symptom 4/5 is purely a host-side interception issue.
3. Add a host-level (`api.keymap.registerLayer`) guaranteed-exit binding independent of the embedded OpenTUI `useKeyboard` Escape handling, so users are never trapped even if the root cause of Symptom 4/5 turns out to be (also) a host-integration limitation that can't be fixed from the plugin side alone.
4. Fix the confirmed secondary code defects found in review: add `key.preventDefault()` to Landing's arrow/Enter branches for consistency with every other screen; give `safeScreenMount` a real 3rd fallback-close parameter (or drop the dead argument at every call site); wire real forward/back pagination in `Catalog` (`onPage` is currently a no-op); remove or actually use `rendererMissingReported`; log (at least once) when the custom renderer becomes unavailable; guard `create.tsx`'s Enter-vs-`onSubmit` double-fire on text-input steps.
5. Add real interaction tests: mount each screen through the actual (or a faithful) OpenTUI/Solid render + `renderer.keyInput`/mouse event simulation, asserting Enter selects the focused item, Escape closes/returns, and a simulated mouse-down on a rendered button's real hit-test box selects it — closing the test-coverage gap identified above (confirmed and sharpened by Judgment Day: the test mock has no `api.ui.Dialog` at all, so every "integration" test silently exercises only the legacy fallback branch) so a future "review approved" claim is trustworthy for this class of bug.
6. Re-verify manually in a real terminal (the native FFI/renderer limitation that blocked local verification during the original implementation is exactly the gap that let this ship broken) before claiming the fix works.
